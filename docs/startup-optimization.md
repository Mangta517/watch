# 手表启动优化版使用说明

配套固件：F411-SPP-Startup-Optimized.hex。配套手机调试器：Bluetooth-Wave-Startup.apk，版本1.95-wave.8，versionCode 13。

## 本次改动

| 流程 | 原流程 | 新流程 |
|---|---|---|
| 传感器任务创建 | 等RTC和蓝牙初始化结束 | 首帧提交后立即创建 |
| RTC的LSE启动 | 在LVGL任务等待就绪或超时 | LVGL每次循环检查就绪，保持原5秒超时 |
| 蓝牙上电及AT配置 | 连续等待上电、响应、保存、重新上电 | 在原LVGL任务分阶段推进，等待期间继续刷新界面 |
| MPU零偏校准 | 占住sensor任务，其他传感器服务暂停 | 利用正常采集帧逐步校准，其他服务继续运行 |
| 启动测量 | 通过历史最大间隔推断 | SPP记录各阶段真实时刻、状态和校准帧数 |

保留两个任务的优先级、栈大小、5ms/10ms目标周期，以及原I2C、LCD和触摸时序参数。
蓝牙保留20ms放电、1200ms启动、500ms查询超时、100ms参数保存等待；配置已有且匹配时不重复写入，修改后仍重新上电并查询验证。
AT初始化期间独占串口接收；手机业务接收等蓝牙初始化和RTC等待结束后恢复，提前到达的校时消息暂留原接收缓冲。清屏不会清掉初始化响应；业务发送不会提前消耗心率队列。
UART发送本身仍为原阻塞接口，启动AT单次发送超时上限10ms。RTC就绪后的HAL配置与备份恢复沿用原实现。

校准保留原静止/水平门限、连续100帧静止和100帧平均，Z轴保留1g。
优化让等待与其他工作重叠，没有缩短校准所需的有效采样帧数。
静止等待3秒、平均阶段2秒按真实经过时间超时；失败保留旧偏移、继续采集，不自动增加重试逻辑。
校准完成前IMU已开始发布数据，此时尚未完成本次零偏修正；平放静止直到诊断显示完成，再判断姿态和漂移。

## 烧录和连接

1. 使用现有Keil/ST-Link流程烧录配套HEX，然后重启手表。HEX为当前F411手表的完整固件，起始地址0x08000000。
2. 安装配套APK，通过原连接入口连接手表经典蓝牙SPP。SPP名称沿用模块当前名称，BLE名称仍为F411-Watch。
3. 点击「FreeRTOS / 传感器诊断」。固件默认发送，不必开启心率才能看到启动阶段。
4. 重启后先平放静置，等校准显示完成，再导出诊断CSV。

未在本次工作中烧录板子或安装手机APK；手机连接与屏幕表现需要实测。

## 看哪些时间

手机顶部「启动阶段」显示板端HAL毫秒时刻及阶段耗时，不使用手机收到消息的时间估计启动耗时。

| 字段 | 含义 |
|---|---|
| 首帧提交 | lv_refr_now返回后的时刻，不等于LCD DMA已完成 |
| 正常采集开始 | sensor初始化结束，进入正常服务循环前的时刻，不代表所有器件已经产生有效转换结果 |
| 传感器初始化结束 | 现有传感器初始化、数据服务初始化、首次电池读数和AHT21初始化完成 |
| RTC结束/耗时 | LSE等待及原RTC配置、备份恢复的结束时刻和总耗时 |
| 蓝牙结束/耗时 | 上电、查询、必要的修改及重新上电验证的结束时刻和总耗时 |
| MPU校准状态/帧数 | 等待静止、采样平均、完成或失败；稳定帧和平均帧分别累计到100 |
| 校准结束/耗时 | 从校准begin到完成或失败的实际经过时间 |

未发生的阶段显示「--」，CSV保存为4294967295。
RTC/蓝牙HAL结果：0成功、1错误、2忙、3超时。校准结果：0成功、1失败。
CSV新增type=4、name=startup；采集开始字段为sampling_begin_ms，校准耗时为calibration_end_ms减calibration_begin_ms，按32位无符号时间差处理。
校准状态：0尚未开始、1等待静止、2平均、3完成、4失败。

即使手机连接得晚，仍能收到保存的本次启动阶段记录，无需在上电瞬间已连接。
约每1.1秒发送一组：3个任务、6个传感器、系统和启动各1条；最近1024条记录约覆盖93秒。
诊断每100ms最多发送1帧，沿用原UART发送路径；诊断自身会影响任务耗时。

## 建议的板端复测

1. 平放冷启动3次，分别导出CSV，记录正常采集开始、RTC/蓝牙结束和校准结束的时刻及结果。
2. 看ADC首批成功读取之间是否仍有原先约3.4秒的启动空窗，并对照校准进行时AHT21、磁力计等成功读取计数是否增长。
3. 启动时轻微移动一次，确认校准失败时其他采集与界面仍能继续。再平放重启，确认能完成校准。
4. 蓝牙模块参数已正确时再次重启，确认初始化成功，且没有再次修改配置和重新上电验证的额外等待。

这份导出之前没有各阶段直接时间戳，原3.445秒ADC最大间隔只能说明启动空窗，不能单独当作MPU校准耗时。
本版的实际缩短量应以成品板导出的启动记录为准；普通任务循环约11ms的问题属于后续运行性能优化。

## 已完成验证

真实C任务入口测试覆盖RTC/蓝牙等待期间的首帧、UI服务和传感器服务，以及任务分配失败路径。
MPU驱动测试覆盖原校准结果、偏移累加、运动/NACK不提交、分步校准、10ms计数门限、时间回绕、真实时间超时及无额外I2C/等待。
蓝牙测试覆盖分阶段上电、参数保存、重新上电验证、已有配置、静默/收发失败、参数拒绝、恢复和时间回绕。
RTC测试覆盖分阶段LSE等待、超时、时间回绕、保留备份时间及最终配置失败。
原sensor、startup、BLE、UI、clock及diagnostics主机回归通过；UI验证AT期间不抢接收数据、不取走心率队列。
Java直接解析真实C输出的诊断字节，验证启动字段、全部拆包位置、混合心率帧、CRC、CSV和缓存。
Keil构建0错误/0警告；APK构建成功，v1/v2/v3签名和zipalign通过，工具仍报告原有32条警告。

这些是源码、主机模拟、构建和签名结果，不是板端启动时间或手机真实收发证明。
