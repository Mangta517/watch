## 错误在哪里

### 1. 早期 GPIO 已经驱动 WDI，驱动初始化再改高阻太晚

`aefd183`、`76bdcf5` 的 `Core/Src/gpio.c` 在 `MX_GPIO_Init()` 中预置 PB2/WDI 为低电平，并把它加入推挽输出组。随后 `App_Task_Create()` 才调用 `tps3823_init()`，把 WDI 改回高阻。

非 A 版 TPS3823 在 RESET 有效期间收到 WDI 跳变可能锁存复位。启动阶段先强拉低 WDI，存在触发该行为的路径。仅在后面改高阻、等 301ms，不能保证解除已经发生的锁存。

修复：从最初 GPIO 初始化起，PB2 保持 `GPIO_MODE_INPUT / GPIO_NOPULL`，同步 `.ioc` 为 `GPIO_Input`；正式启用时保持复位屏蔽，等待正常复位延时，再切换推挽输出、产生喂狗脉冲，最后拉低 PB1 接通复位保护。已锁存的非 A 版需要完全断电重上电。

依据：TPS3823 手册第 15 页 7.3.4、第 17 页 8.2.2，以及 [TI 官方工程师说明](https://e2e.ti.com/support/power-management-group/power-management/f/power-management-forum/769155/tps3820-phenomenon-for-reset-pin)。

### 2. 单次翻转不保证每次调用都有下降沿

两版旧 `tps3823_feed()` 都只执行 `HAL_GPIO_TogglePin()`。按手册下降沿刷新超时计算，两次调用才保证一次有效下降沿，较慢任务处理可能把有效喂狗间隔拉长。

修复：每次调用输出一次高脉冲并回到低电平，中间保留 16 次 NOP。已检查 ARMCC5 `-O3` 反汇编，两次电平写入和 NOP 循环均存在。

### 3. 只在显示任务循环末尾喂狗，未覆盖长刷新过程

旧版本在首帧和 sensor 首轮完成后接通看门狗，并依赖显示任务完成一整轮服务后才检查喂狗。长刷新期间没有分块喂狗；DMA 若在 CPU 渲染期间已经完成，也不一定会进入 DMA 等待，低优先级 sensor 可能迟迟得不到调度。

修复：在显示任务侧按新分块进度检查喂狗，运行期分块间让出一拍，仍要求 sensor 有新循环进度。首帧、sensor 启动和显示服务分块喂狗均有时间预算，不采用中断无条件喂狗。LCD DMA 丢失回调时，通过任务侧超时收尾确认缓冲区安全后释放刷新状态。

### 4. 调试工作区曾关闭全工程优化，主机测试未反映实板速度

出现问题时，工作区 Keil 目标为 `Optim=1`，读取全部 252 个 C 对象的实际 ArmCC 命令均为 `-O0`。这会同时放慢 LVGL、HAL 和按循环次数延时的软件 I²C，不能用主机桩指定的分块耗时证明实板满足最短 900ms 看门狗超时。

恢复历史 `Optim=4 / -O3` 后，全量编译确认 252 个 C 对象均使用 `-O3`。`-O0` 本身不是逻辑错误，但切换后必须重新验证实际时序。

**归档边界：** `aefd183`、`76bdcf5` 原提交自身已经是 `-O3`，不能把它们标成 `-O0` 版本。此次出现 `-O0`、仅补分块喂狗但仍复位的中间状态当时没有独立提交；这里记录其编译证据和已知差异，不伪造一个“原始错误提交”。

## 修复验证与结论

- 用户先反馈仅增加分块喂狗后仍然重启；随后恢复 `-O3` 并修正 WDI 启动状态后，用户明确确认问题解决。
- 这些修改作为组合通过实板反馈，未逐项回退隔离，不能断言每项都单独造成了本次实板复位。
- watchdog 测试已覆盖真实 `MX_GPIO_Init()`，不再仅从 `tps3823_init()` 开始；startup 覆盖长首帧、运行期长刷新、任务停滞和计数回绕。
- 全量 ARMCC5 编译为 0 错误、31 条未改动 LVGL 库警告；已核验实际优化参数和喂狗反汇编。后续温湿度表盘修改增量编译为 0 错误、0 警告。本次归档不重新烧录。

电路另外存在 U9 ENB/PB1 没有外部上下拉的缺口，R29 上拉的是 A1，不是 ENB。MCU 复位窗口的选路电平及 PA3 释放时 TPS_EN/3V3 是否保持，需要硬件确认；不把这些未隔离验证的风险直接写成已证实根因。
