# F411低功耗策略

## 2026-11-19 待机功耗修复

- SENSOR 总线空闲时保持开漏释放。SDA 在开漏输出模式下写高即可读 ACK/数据，省掉字节间方向切换及每个 25ms 采样周期的挂起与恢复。84MHz APP 的 SENSOR 位延时为 100 次循环，EEPROM 与触摸为 67 次循环。计步与抬腕继续每 25ms 采样，熄屏基础服务继续每 200ms 运行。
- RTC 负责 STOP 区间计时。脱离调试器时，进入 STOP 前关闭 DWT 周期计数和 CoreSight 跟踪使能，唤醒后恢复。ADC1 仅在采样时开时钟，未接 HSE 的 PH0/PH1 配为模拟无上下拉，LCD 休眠期间释放片选。
- 亮屏表盘无交互 500ms 后，LVGL 和触摸轮询由 10ms 放宽到 20ms。触摸、按键、页面切换或进入功能页时使用原有活跃节拍。自动熄屏仍用 10 秒超时。
- 熄屏自动心率持续判定无信号约 3 秒时提前关灯。上板可对比 SENSOR 的 SCL/SDA 波形、熄屏静放电流、佩戴心率成功率及首步/抬腕响应。

## 2026-11-17 计步采样修复

日常亮屏、指南针和熄屏均使用MPU6050的40Hz低功耗加速度循环，`PWR_MGMT_2=0xC7`、`PWR_MGMT_1=0x28`。心率/SPORT使用100Hz连续加速度；三轴先做25ms时间常数低通，再保留余量按20/30ms交替送入计步层，平均40Hz。`LP_WAKE_CTRL=3`对应40Hz，依据厂商寄存器手册第43页。[InvenSense寄存器手册](https://www.mouser.com/datasheet/2/306/RM-MPU-60xxA_rev_4-736751.pdf#page=43)

sensor基础周期为25ms，亮灭屏切换沿用采样连续性，温湿度/气压窗口保持该周期。NOT_READY最多两次5ms补读。LVGL熄屏基础服务为200ms，串口待收和新抬腕事件立即通知；抬腕条件改为放下、观看各持续400ms。该版本软件I2C每轮空闲挂起、下轮访问前恢复。

MPU恢复接口返回失败冷却时，清除旧帧补读请求。熄屏后台在冷却期间按200ms服务，温湿度/气压窗口将周期收紧到100ms，指南针、气压待机重试及在途EEPROM事务将周期收紧到25ms。心率/SPORT继续使用原采样节拍，MPU恢复推进后回到25ms并等待新转换。

计步使用模长三点FIR和12ms平滑，普通姿态峰谷门限0.080g，正面朝上为0.120g。步间隔250～1500ms，并检查相邻间隔与平滑步频的比例0.65～1.55。强信号连续3步、弱信号5步确认后回补，后续每步至少回落半个峰谷差且不小于0.045g后输出。三轴波动不超过0.045g并持续450ms时屏蔽候选，连续步态按已测步间隔加200ms清理，最长1500ms。未确认步行时，短时方向明显变化会取消候选并抑制250ms。幅值有效区间为0.35～3.8g，断采超过600ms重建连续状态。亮屏表盘每100ms按步数变化更新文字和圆环。规则与验证详见[计步响应优化记录](../work/step-response-20261117/验证记录.md)。

本次选择常开40Hz采样以覆盖起步和窄脉冲步态，CPU与I2C访问频率随之增加。实际器件输出率、佩戴计步准确率和电池端平均电流须在实板测量，既有续航估计需要结合本版电流重新评估。下方日期小节记录各历史版本。

## 2026-11-16 核查修复

MPU6050的INT接有4.7kΩ外部上拉。初始化及故障恢复统一使用`INT_PIN_CFG=0xC0`，配置为低有效、开漏、50µs脉冲，`INT_ENABLE=0x01`。空闲时释放INT，避免原推挽无效低电平经上拉持续灌电流。`INT_RD_CLEAR=0`使DATA_RDY状态保留到读取`INT_STATUS`，sensor继续按原周期轮询。PB12保持开机屏蔽，采样、计步、抬腕与看门狗节拍沿用当前200ms路径。寄存器行为依据厂商手册4.15～4.17节，电流收益待实测。[InvenSense寄存器手册](https://www.electrokit.com/upload/product/41013/41013621/RM-MPU-60xxA_rev_4.pdf)

移除已无生产调用的静止查询及10秒判定状态机，计步与抬腕统一使用600ms断采界限。三条软件I2C总线依靠原理图上的外部4.7kΩ上拉，关闭SCL/SDA内部上拉。APP位延时为67/134次，100MHz主引导与保底恢复为80/160次。触摸START/STOP注释与开漏配置对齐，CubeMX及生成RTC初始化统一为0/32767。

## 蓝牙

在Settings → Bluetooth详情页下方，点击`BLE: ECO / SCREEN OFF`与`BLE: KEEP CONNECTED`切换模式。默认ECO，重启恢复ECO；模式只保存在RAM，不写入EEPROM。

ECO模式熄屏后等待初始化、接收队列、当前发送与维护事务完成，再等待安静期才断电：未确认手机通信时仍为1秒；已收到合法校时消息、`phone_ready`置位时为30秒（2026-11-15），便于熄屏后选择BIN并启动OTA。屏幕切换及收发活动刷新计时，OTA请求受理后由原事务忙状态继续保持供电；断电、接收错误及运行时长报告发送失败会清除手机就绪标志。这里没有可靠连接状态输入，单纯BLE连接不能触发30秒宽限。亮屏后通过原分步初始化恢复，需等待模块启动及手机重连，关闭期间不能接收校时、天气和诊断。选择保连模式时熄屏后仍保持BLE供电及USART1接收这些命令。SPORT始终关闭蓝牙。未使用固定返回0的`kt6368a_is_connected()`作为断电依据。

模块关闭时沿用UART停用和PA9/PA10模拟输入流程，保留完整天气缓存和RTC。安静期没有手机ACK含义。30秒宽限期间仍保持BLE/USART1供电并使用Sleep保障接收，代价仅发生在手机就绪且熄屏的窗口内；没有实测电流，不能据此量化续航。默认ECO安静期满断电、SPI/DMA/ADC空闲时进入STOP；选择保连时蓝牙常开，熄屏仍使用Sleep保障串口接收。

## 2026-11-03 STOP期间临时屏蔽MPU DATA_RDY（较早方案，已由当前开机常驻屏蔽覆盖）

MPU6050的INT是锁存输出，PB12 EXTI回调只计数并置标志，应用没有读取这些标志：sensor按10/20/200/400ms自身任务期限直接读INT_STATUS和数据。原实现只在期望等待超过200ms时才屏蔽PB12，短STOP仍可能被器件锁存的DATA_RDY提前结束并多一次HSI→PLL恢复。现改为所有真实STOP在进入前保存`EXTI->IMR`并清除PB12位，唤醒后精确写回原值；PA4、RTC及其它EXTI位始终保留，不清`EXTI->PR`、不清NVIC pending，也不改变Sleep回退、各STOP否决条件、时间补偿和任务采样周期。

主机测试覆盖5/10/100/200/400ms STOP在STOP期间收到新的DATA_RDY事件时仍按RTC期限结束、`EXTI->PR`保留、PA4可提前唤醒及原已屏蔽位不被擅自打开；屏蔽前已置位的NVIC pending仍可能让WFI立即返回，本次改动只减少而不会完全消除MPU造成的提前唤醒。Codex独立回归startup、sensors、clock、ble、watchdog、tickless均通过；旧版`app_tickless.c`配新harness恰在`stop_exti_early==0`断言失败，新版通过；普通APP与升级APP的Keil ARMCC构建均0错误、0警告，日志为`MDK-ARM/build_lowpower_20261103_normal.log`和`MDK-ARM/build_lowpower_20261103_upgrade.log`，已生成HEX；未烧录、未测电流。

## 2026-11-03 MOT 运动唤醒研究结论（历史）

当时未启用MPU MOT（运动）硬件唤醒，采用5Hz低功耗循环和400ms静止软件轮询。研究结论：MOT 主要收益是省去 CPU 与 I2C 轮询；但 `app_imu_is_stationary()` 与 `common_activity` 在约 600ms 无新帧后会退出静止判定并重置抬腕及步态状态，驱动侧“1s 无帧恢复”需要区分是器件异常还是有意等待；要真正以 MOT 唤醒替代轮询，还需补充 ISR→任务通知通路、进入 STOP 时保留运动检测所需的 PB12（与本轮屏蔽 PB12 的取向相反），并结合实板起步、抬腕与误唤醒验证。仅写寄存器不足以安全启用，故本轮不做该改动。

## 2026-11-04 静止慢待机放宽到1秒与暂停看门狗（历史，2026-11-15已替代）

以下记录当时的1秒慢待机及WDI高阻方案。2026-11-15已取消该方案，当前固定200ms读取、看门狗连续计时，以本文开头与[看门狗说明](watchdog.md)为准。

- 慢待机节拍：稳定熄屏且加速度连续约10秒不变后，普通熄屏的CPU读取与基础服务节拍由400ms放宽为1000ms（`APP_SENSOR_SLEEP_IDLE_POLL_MS`），sensor发布给LVGL的通知等待超时同步为1000ms；出现新运动时同一轮就回到200ms（`APP_SENSOR_SLEEP_POLL_MS`）。心率10ms、SPORT、亮屏刷新、姿态页以及温湿度/气压转换与恢复窗口的100ms检查维持原周期，不因慢待机放宽。
- 采集代价：MPU器件输出率仍是5Hz，慢待机只是CPU每秒读一帧，两次读取之间器件产生的帧被丢弃，短动作可能漏采，抬腕判定的延迟也可能增加。活动层断采容忍随之分档：非静止仍为600ms（`COMMON_ACTIVITY_MAX_GAP_MS`），已静止放宽到1200ms（`COMMON_ACTIVITY_STATIONARY_MAX_GAP_MS`），使1秒读数加调度抖动不会反复作废静止、计步与抬腕的连续判定；真正超档时只清连续性，累计步数和已发布抬腕序号保留。
- RTC计时：睡眠补偿改用一分钟内的“秒＋亚秒”计数，并按一分钟模数计算差值，避免睡满1秒被原亚秒模减算成零，同时覆盖跨分和午夜。
- 外部看门狗：TPS3823最短硬件超时仍是900ms。距最近一次由新sensor进度确认的双任务喂狗不超过200ms（`APP_WATCHDOG_STOP_WINDOW_MS`）且当前为1000ms静止慢待机节拍时，`app_task_watchdog_stop_allowed()`授权本轮所有实际IDLE等待路径（含短STOP、普通Sleep以及RTC不可用回退的1ms WFI）把PB2/WDI切为高阻，暂停芯片超时计时；PB1/WDG_EN保持低电平，芯片欠压复位通路仍然接通。醒来立即恢复推挽输出并补一次喂狗脉冲，该恢复路径不更新`app_watchdog.last_feed_ms`，因此200ms授权窗口不会因暂停本身续期；sensor或LVGL停止推进后授权自然失效，长等待被收紧到400ms（`APP_TICKLESS_WATCHDOG_PAUSE_MIN_TICKS`），任务停滞仍会被硬件超时复位。单次STOP上限仍为1000ms，不存在“超过1000ms的STOP”。
- 残余风险：授权期内如果RTC/LSE永不唤醒（LSE停振且无其它中断到来），WDI高阻期间无法依靠看门狗超时复位，只能等唤醒后恢复喂狗，此路径需实板评估。

本轮只涉及软件节拍、活动层容差与看门狗暂停逻辑；未烧录、未测待机电流，也未做实板计步/抬腕精度与唤醒时延验证。Codex已独立运行startup、sensors、tickless、clock、watchdog、touch、UI七套主机回归，全部通过；普通APP与升级APP的ARMCC 5.06全量构建均为0错误、13条既有LVGL警告。
