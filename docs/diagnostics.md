## 使用

1. 编译并烧录调试固件，重启手表并等待蓝牙初始化完成。普通APP和升级APP仅BLE，查询结果为T4+01、T5+00；只有Bootloader的OTA升级模式开启SPP。诊断输出仍须在编译时开启APP_DEBUG_TELEMETRY。
2. 安装配套 APK，可覆盖原波形调试器（同包名、同签名）。使用BLE扫描并连接F411-Watch，选择FFF0/FFF1并开启Notify；手表正常运行和熄屏均不开放经典蓝牙SPP连接。
3. 点击「FreeRTOS / 传感器诊断」。固件默认自动发送，约每秒更新一组诊断；无需先开启心率。心率读取计数需要在手表心率页点击 START。
4. 点击「导出 CSV」分享最近 1024 条诊断记录，连续接收约 102 秒。保留原心率波形及其 ZIP 导出入口。
5. 「关闭发送」发送 DIAG,0 加实际换行，停止诊断 UART 输出，计时与统计仍运行；「开启发送」发送 DIAG,1 加换行。停止后旧数据显示为「数据已旧」。命令复用原原始发送入口，BLE 仍需选择 FFF0/FFF1 并开启 Notify。

## 启动阶段

新版在首帧提交后立即创建sensor任务，RTC的LSE等待与蓝牙启动通过LVGL循环分步推进。
MPU有有效EEPROM记录时恢复六轴零偏并跳过静止校准；没有有效记录时使用正常采集帧校准，保留100帧静止和100帧平均。
校准成功才保存到EEPROM 0x60..0x9F，不覆盖原磁力计记录。手机可点击「MPU重新校准并保存」，发送IMU,CAL加换行。
手机诊断顶部显示首帧提交、传感器初始化/正常采集开始、RTC/蓝牙结束与HAL结果、校准状态/帧数/结束时间。
各时间为HAL毫秒计数从0开始后的时刻，不是手机收到消息的时刻；首帧提交不等于屏幕DMA完成。
校准成功前IMU已发布未完成本次零偏修正的数据；静止平放直到完成后再判断姿态和漂移。
未发生的阶段用0xFFFFFFFF表示；校准结果0成功、1校准失败、2校准成功但保存失败；校准状态5表示EEPROM恢复且跳过本次校准。HAL结果0成功、1错误、2忙、3超时。
校准稳定等待3秒、平均阶段2秒按实际经过时间判断超时，失败不提交部分偏移并继续正常采集。
启动测量见startup-optimization.md；当前EEPROM流程和操作步骤见imu-eeprom.md。

## 指标含义

| 指标 | 含义 |
|---|---|
| 栈总量 / 历史最小余量 | 当前 lvgl 4096B、sensor 2048B、IDLE 512B；FreeRTOS 栈填充值扫描结果乘 sizeof(StackType_t)，转换为字节 |
| 栈占用峰值 | 总量减历史最小余量，是填充值法估计值，不是当前即时栈指针用量 |
| CPU 百分比 | 相邻诊断快照之间的 FreeRTOS 运行计数差 / 总计数差；调度归属时间包含 ISR，不是剥离所有中断后的纯任务执行时间 |
| 任务周期 | 连续两次业务循环开始的间隔，最近/历史最小/历史最大，单位 us；首拍尚无间隔。Idle 无固定业务周期，不伪造循环指标 |
| 处理耗时 | 循环开始到处理完成，排除末尾周期等待，包含被抢占、内部等待和诊断发送时间，最近/历史最大，单位 us |
| 超预算 | 单次处理耗时大于任务原周期预算：lvgl 5ms、sensor 10ms；它不是全部调度截止时间违约的计数 |
| 传感器读成功 / 未就绪 / 错误 | 来自真实读取结果，分别统计；传感器未就绪不会计为通信失败 |
| 数据年龄 / 成功间隔 | 从最近成功读取起经过的 HAL 毫秒时间、两次成功读取的间隔；尚无成功读数显示 --。读取成功不保证器件内部完成了新一次转换 |
| 读取耗时 | 实际驱动读取前后计时，100us 分辨率；包括抢占。SPL006 包含既有压力补偿调用，ADC 包含启动、转换等待及停止 |
| RTOS / LVGL 内存 | FreeRTOS 堆当前/历史最小剩余；LVGL 池当前剩余/诊断快照观测到的最大占用，全部为字节。短于快照间隔的瞬时峰值可能遗漏 |
| 心率队列丢弃 | 32 帧队列满时丢最旧帧的累计次数；STOP、重新 START 或故障清队列属于原流程，不计入溢出 |
| 心率 UART 成功 / 失败样本 | 真实 C 发送函数的返回结果，按发送批次的样本数量统计；成功只证明字节交给模块，不证明手机收到 |
| 手机 CRC / 序号缺口 | 诊断帧 CRC/格式拒绝和已接收帧之间的序号缺口；缺口可能来自板端 UART 失败或后续链路，需对照板端计数 |

MPU6050、LSM303DLHC、EM7028、SPL006、AHT21 和电池 ADC 分开显示。EM7028 初始化字段在 START 时更新为最近启动配置结果。
返回码沿用各驱动枚举；SPL006 将压力返回码放低 8 位、温度返回码放次低 8 位，0x10000 表示压力补偿失败。
AHT21 触发命令成功不算读取成功，触发失败计入错误；忙轮询计入未就绪，最终超时计入错误。电池初始化 0 表示服务初始化完成，转换是否正常应看读取结果。

## 实测建议

先静置 30 秒，再持续滑动/切换页面 30 秒，然后开心率 60 秒并导出两种 CSV。
观察 sensor 周期是否明显超过 10ms、成功读取间隔是否拉长、读取/初始化错误是否增加、心率队列和 UART 失败是否增加。
气压器件 1Hz、1s 轮询，未就绪较多属于预期；AHT21 约 2 秒一轮，心率读取下限 30ms，不能统一按10ms判断所有器件。MPU仍为100Hz，DATA_RDY有效才计成功，每次服务最多发布一帧。成功计数表示实际取得的新帧，不代表器件生成的全部帧；普通寄存器被新样本覆盖不会产生I2C错误。

常规轮询观察MPU的`gap_max_ms`、`work_max_us`和sensor任务周期；读取间隔超过10ms提示可能跳过中间样本，但没有硬件帧号时不能精确统计漏采帧数。`errors`只表示驱动返回失败，`not_ready`表示本次未取得新帧，均不能替代完整采样率测量。
栈余量应在页面切换、校准、传感器失败等实际高负载路径后再观察。

诊断复用原 USART1 中断异步发送：每 100ms 最多一帧 30～78 字节，约 2.6～6.8ms 线速时间，超时预算仍为 10ms，在 LVGL 循环轮询时检查。
帧保存在固定静态缓冲中，UART完成后才累计成功；超时或断电累计失败，HAL_BUSY不推进本行和序号。关闭发送后仍收取在途帧结果。
调试版心率每次最多2帧，以静态缓冲异步发送；心率与诊断各自收取自己的完成结果，未收取结果前其他异步发送等待。AT/业务写入不会穿插到在途帧中，RX继续使用原接收中断和环形缓冲。
当前 3 个任务 + 6 个传感器 + 1 条系统记录 + 1 条启动记录 + 1 条MPU EEPROM记录 + 1 条MPU校准判定记录，一组约 1.3 秒、798 字节；没有 printf、动态分配或新增发送任务。
诊断不再在 LVGL 任务忙等 UART 线速时间，但打包、快照和发送中断仍占用 CPU。可关闭发送一段时间再开启，对照 CPU 窗口、最近周期和成功读取间隔；历史极值不会因开关而清零，干净的重复实验需重启。
CPU 计数器约 119 小时回绕，本内核在回绕处的运行统计不保证准确；长时间实验应在此前重启，不把该窗口作为精确 CPU 统计。

## 协议与导出

WDG1 二进制帧：4 字节 ASCII 标识、类型 uint8、对象 ID uint8、帧序号 uint16、板端快照时间 uint32、若干 uint32 字段、CRC16。
全部多字节字段小端。CRC 为 CRC-16/CCITT-FALSE（多项式 0x1021、初值 0xFFFF、无反射、无最终异或），覆盖帧头和数据。
类型 1 任务含 14 字段，类型 2 传感器含 10 字段，类型 3 系统含 16 字段，类型 4 启动含 16 字段，类型 5 MPU EEPROM含 4 字段，类型 6 MPU校准判定含 16 字段；确切顺序见 DiagnosticParser.FIELDS及imu-eeprom.md。
无有效采样时 sample_age_ms=0xFFFFFFFF。任务 ID：0 lvgl、1 sensor、2 IDLE；传感器 ID 依次为 MPU、MAG、HEART、BARO、AHT、ADC。
同一组记录使用同一个快照时间；各传感器在短临界区分别取一致快照，并不是所有器件同时转换。

手机在原 SPP/BLE 接收副本上解析诊断并将剩余字节交给原 JustFloat 波形解析器，不新增 socket 消费者。
支持任意拆包、粘包、CRC 拒绝及后续帧恢复。损坏诊断帧返回原字节流用于重新同步，可能使相邻一帧波形被旧 JustFloat 解析器拒绝；正常完整诊断帧不进入波形解析。
CSV 是长表：phone_elapsed_ms,device_ms,sequence,type,name,field,value。phone_elapsed_ms 为手机完整诊断帧到达时间，device_ms 为板端快照时间，字段名称包含单位；未知值原样保存 4294967295。
手机不保存无限时长记录，最近 1024 帧以外的历史会淘汰。关闭页面仍接收；重连清空旧诊断数据。

## 2026-10-21：触摸滑动时 MPU6050 链路中断（FIFO版本历史记录）

现象：触摸滑动时 MPU6050 数据消失，界面显示 `NO IMU DATA`、pitch/roll/yaw 变 `--`，松手后自行恢复；磁力计读数正常。

当时的FIFO版本定位到时间戳与新鲜度判定组合，以下机制和主机数值为历史记录；当前已关闭FIFO，不再执行这条积压路径：

1. `mpu6050.c` 从 FIFO 深度回推每帧时刻（`next_ms = counted_ms - (深度-1)×10ms`），一次服务最多取 8 帧，剩余留在器件里。
2. 任务被抢占造成的积压越大，这一批帧的估算时刻越旧。主机套件实测（磁刚读成功后压入不同帧数、跑一次服务）：

   | 压入帧数 | 服务后剩余 | imu_online | mag_online | 末帧时刻 |
   |---|---|---|---|---|
   | 12 | 4 | 1 | 1 | −40ms |
   | 14 | 6 | **0** | 1 | −60ms |
   | 20 | 12 | **0** | 1 | −120ms |

3. `app_imu.c` 用 `HAL_GetTick() - s_last_sample_ms < 50ms` 判在线，而 `s_last_sample_ms` 是上面的回推时刻，于是"帧一直有、却追不上窗口"被当成没有数据。阈值 14 帧约等于 140ms 的连续积压。
