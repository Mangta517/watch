# FreeRTOS 与传感器诊断（2026-10-14）

## 2026-10-28：磁新样本与sensor读取峰值

本次保留已经修正的超期等待策略，调整正常读取的事务安排：先服务30ms下限的PPG，本轮有PPG事务则延后磁轮询；MPU仍逐轮读取。心率服务以返回值报告实际总线使用，未到读取时刻不占磁轮询槽位。原始PPG高/低/高三读、SENSOR位延时、器件档位和新鲜度限制均保留；没有修改触摸、显示调度、Flash或UART接收。

磁力计只有DRDY=1、LOCK=0且完整帧有效才计成功。LOCK残留即使伴随DRDY也只排空、不计新帧，不刷新年龄；校准计数遵守同一结果。常规融合允许在原窗口内使用最近的磁参考，重复使用参考不增加传感器成功数。[磁力计说明](magnetometer.md)记录配置输出率、读取率差异和DRDY清除尚需实板验证的边界。

真实`app_task.c`耗时模型使用MPU=5ms、MAG=3ms、PPG=3ms：错峰后3000ms运行300轮、99次PPG读取，无普通读取超预算；此前同类8ms IMU/磁+3ms PPG模型为3006ms/282轮。持续15ms工作、120ms抢占、恰好到期及tick回绕仍保留一拍让出，电池、气压和看门狗继续推进。这是固定耗时模型，未测量本次板端时间；初始化、恢复、环境/EEPROM/Flash访问和抢占仍可能使整轮超过10ms。

独立75Hz转换模型在3秒内产生225帧：无PPG时225帧被接收；错峰模型接收174帧（约58Hz），其余可能被后续转换覆盖。因此优化优先保留MPU和PPG节奏，代价是磁采集率下降，不能按硬件75Hz声称采齐。新增回归同时验证无DRDY、相同数值的新帧、LOCK、磁延后超龄、校准计数和跨tick回绕；运动心率回归补测上一拍10ms加速度参考。

传感器、startup、UI（诊断开/关）、diagnostics及reset_ble五套主机回归通过。普通APP/升级APP的Keil ARMCC构建均0错误、0警告，MAP ROM均219368字节，RW+ZI均104216字节，已生成两套HEX；未烧录。

实板复测应在心率正常工作、PID校验通过时分别静置/滑动采集至少60秒诊断。用同一板端时间窗口内的success增量计算MPU、MAG、HEART实际读取率，并对照not_ready、errors、work_max_us、gap_max_ms和sensor超预算增量。成功数仍不能证明零漏采；DRDY清除和真实转换率须由寄存器/引脚波形确认。PID=FF恢复、触摸轮询及Flash/蓝牙连续接收测试留待后续项目。

偶发重启的现场保留与手机查询见[复位诊断](reset-diagnostics.md)。

## 当前测试方式（2026-10-28）

普通APP和升级APP使用64MHz、Scale3、Flash 2等待周期，APB1=32MHz、APB2=64MHz、SPI1=32MHz。Tickless默认启用STOP；BLE开启时仍使用Sleep保证UART接收，SPORT熄屏且外设空闲时可进入STOP，醒后恢复64MHz并补齐HAL/RTOS/TIM2时间。TIM3仍以1MHz计数，屏幕睡眠后停止计数并关闭TIM3/SPI1/DMA2时钟，亮屏恢复；软件I2C/触摸按64MHz缩放位延时。`app_tickless.h`的`APP_TICKLESS_ENABLE_STOP`默认为1。此前84MHz/Sleep采集记录保留为历史数据，不能直接用于当前配置的功耗或业务耗时结论。

默认`APP_DEBUG_TELEMETRY=0`：启动不发送诊断、心率波形或SEND TEST。现在手机`DIAG,1`加实际换行可以单独开启WDG1，`DIAG,0`加换行关闭，无需打开波形编译开关。现有配套App的“FreeRTOS / 传感器诊断”页及CSV继续使用原协议；普通熄屏仍能采集，SPORT按原策略关闭蓝牙，需退出后再连接。

任务ID保持0=lvgl、1=sensor、2=IDLE、3=touch。四个任务报告优先级、状态、栈总量/历史最小余量和CPU占比；lvgl、sensor、touch增加或保留循环次数、周期、处理耗时、超预算及目标周期。touch熄屏后阻塞，唤醒后的周期可能包含整段休眠，驱动恢复等待也计入处理耗时；IDLE不提供业务循环指标。旧手机可能把ID3显示为other，仍对应touch。

1. 烧录对应部署方式的新APP，手机通过BLE连接F411-Watch，选择FFF0/FFF1并开启Notify。
2. 进入“FreeRTOS / 传感器诊断”，点“开启发送”。原始发送也可输入`DIAG,1`并附加CR或LF；反斜杠加n不是换行。
3. 开启后跳过第一组CPU数据，再等一组更新。首次窗口从开机计起，关闭后重开第一组跨越关闭时段；之后才是相邻快照窗口。`cpu_permille`除以10为百分比；IDLE包含Sleep，ISR时间归属于当时任务，不是纯业务指令占用。
4. 分别记录首页后台、持续滑动/切换页面、姿态页、手动心率和普通熄屏，每种至少60秒，记下切换时刻后导出CSV。比较CPU、栈余量、最近周期、最大耗时、超预算及传感器成功次数/错误/间隔；以`target_ms`判断当前动态周期，不能全部按10ms要求。
5. TIM2计时分辨率100us；耗时包含抢占和内部等待。极值和计数从开机累计，DIAG开关不清零；独立极值实验应重启后重测。关闭发送可做负载对照，再开启后跳过第一组CPU数据。
6. 检查Flash重叠风险时，手机持续发送带序号测试行，覆盖启动10秒后的复位日志和每分钟电压追加，至少持续2分钟。比较系统`uart_rx_errors`、`uart_rx_dropped`前后差值，保存手机CRC/序号缺口。错误合计不能单独确认ORE或Flash根因；没有新增错误也不能保证任意连续流无丢字节。本轮仍使用逐字节RX中断。

每组14帧、868字节，按100ms最小帧间隔约1.4秒更新，UART繁忙或任务延迟时更慢。UART完成仅证明交给蓝牙模块，手机CSV/序号才是接收端证据。实板负载、总线时序和Flash重叠尚待上述采集；构建及主机回归见README当前更新记录。

## 2026-10-28：蓝牙心率报错

新固件支持向FFF1写入`HEART,READ`加实际CR/LF，回传一行当前心率状态和故障快照，不依赖DIAG开关，也不触发I2C或重新测量。例如：

```text
HEART,STATE,4,EN,0,FAULT,4,CONFIG,REG,0x0D,VALUE,0xFF
```

STATE为0关闭、1测量中、2有效、3无信号、4错误。FAULT为0 NONE、1 READ、2 WRITE、3 PID、4 CONFIG、5 DATA_CHANGED。REG为故障寄存器，VALUE仅在PID/CONFIG读回不匹配时有效；READ/WRITE的VALUE不能作为有效数据。启动初始化失败也保留现场，后续停止失败不覆盖先前读/启动失败。成功START后快照恢复测量状态。

原WDG1布局保持，下一份CSV/XLSX中的EM7028 `last_result`可携带完整故障：最低字节仍为2（ERROR），第1字节FAULT、第2字节REG、第3字节VALUE。例如`0xFF0D0402`表示CONFIG、寄存器0D、读回FF。成功读取后回到0；普通未就绪仍为1。`init_result=2`仍是初始化/启动错误，启动错误不伪造读取错误次数。瞬时读失败未触发停测时仍沿用原读取结果；详细打包针对启动及导致停测的故障。手机现有App不需更新，保留原始数值后即可解码。

本轮通过电脑BLE执行了一次用户要求的`BATLOG,CLEAR`，设备回复CLEARING_REBOOT后重启；重连STATUS从2217条样本/2469槽变为0条/0槽、READY。只擦sector 7中的电压与复位历史，不影响EEPROM校准及累计运行时间；重启后按原规则重新追加日志。此实板清除使用设备原有固件，不表示上述新增报错固件已经烧录。

## 2026-10-28：sensor串行读取与超期等待

手机CSV在心率稳定段记录到sensor目标10ms，实际约64轮/秒；543轮中274轮处理超过10ms。读取耗时的典型值为MPU六轴4.4～4.5ms、磁力计3.3～3.4ms、PPG3.4～3.5ms，同轮读取时约11.2ms，尚未计入该轮其他业务。这些计时包含抢占，不能直接换算成实板SCL频率。

当前MPU用一笔连续事务读取状态和六轴15字节；磁力计先读状态，再读取六字节磁场，保留DRDY/LOCK处理；EM7028按高/低/高三个单寄存器事务读取，保留跨更新一致性检查和STOP/START时序。总线延时、器件采样配置、融合与错误恢复本轮保持原实现。

已修正`app_task.c`末尾等待：按时完成仍用`vTaskDelayUntil`等待本轮余量；达到或超过周期预算时，改为`vTaskDelay(1)`让出一个RTOS tick，再按实际唤醒时刻重新计时。原先超期后还会额外等待完整10/20/40/100ms周期，现已移除；不会连续补跑过期轮询，也避免持续超期时一直占用CPU、不让touch/IDLE推进。84MHz/Sleep、任务优先级及栈大小保持。

主机回归用真实sensor任务，模拟IMU/磁力计8ms工作及至少30ms一次的额外3ms PPG读取，得到282轮/3006ms（约93.8Hz）、93次PPG读取；旧实现会在“超期只能额外等待一拍”的断言失败。另覆盖持续15ms工作、一次120ms抢占、恰好10ms工作和tick回绕，并检查电池/气压及进度喂狗继续推进。该模型只验证调度行为，不代表实板已经达到93.8Hz或100Hz。

复测时使用同一手机诊断页，心率保持开启至少60秒，再导出CSV；用相邻快照的loops/read_ok增量除以device_ms差值计算真实任务/采样率，比较work_overruns和读取耗时。有效采样增多时CPU占比可能随之升高，应结合完成的有效工作量判断。单轮串行工作仍可能超过10ms，稳定100Hz和实际总线时序需要新一轮实板数据确认。

## 使用

1. 编译并烧录固件，重启手表并等待蓝牙初始化完成。普通APP和升级APP仅BLE，查询结果为T4+01、T5+00；只有Bootloader的OTA升级模式开启SPP。默认构建也支持DIAG,1开启诊断。
2. 安装配套 APK，可覆盖原波形调试器（同包名、同签名）。使用BLE扫描并连接F411-Watch，选择FFF0/FFF1并开启Notify；手表正常运行和熄屏均不开放经典蓝牙SPP连接。
3. 点击「FreeRTOS / 传感器诊断」及「开启发送」，约1.4秒更新一组诊断；无需先开启心率。心率读取计数需要在手表心率页点击 START。
4. 点击「导出 CSV」分享最近 1024 条诊断记录，连续接收约 102 秒。保留原心率波形及其 ZIP 导出入口。
5. 「关闭发送」发送 DIAG,0 加实际换行，停止诊断 UART 输出，计时与统计仍运行；「开启发送」发送 DIAG,1 加换行。停止后旧数据显示为「数据已旧」。命令复用原原始发送入口，BLE 仍需选择 FFF0/FFF1 并开启 Notify。

## 启动阶段

新版在首帧提交后立即创建sensor任务，RTC的LSE等待与蓝牙启动通过LVGL循环分步推进。
MPU有有效EEPROM记录时恢复六轴零偏并跳过静止校准；没有有效记录时使用正常采集帧校准，保留100帧静止和100帧平均。
校准成功才保存到EEPROM 0x60..0x9F，不覆盖原磁力计记录。手机可点击「MPU重新校准并保存」，发送IMU,CAL加换行。
手机诊断顶部显示首帧提交、传感器初始化/正常采集开始、RTC/蓝牙结束与HAL结果、校准状态/帧数/结束时间。
各时间为HAL毫秒计数从0开始后的时刻，不是手机收到消息的时刻；首帧提交不等于屏幕DMA完成。
校准成功前IMU已发布未完成本次零偏修正的数据；静止平放直到完成后再判断姿态和漂移。
未发生的阶段用0xFFFFFFFF表示；校准结果0成功、1校准失败、2校准成功但保存失败；校准状态5表示EEPROM恢复且跳过本次校准。HAL结果0成功、1错误、2忙、3超时。
校准稳定等待3秒、平均阶段2秒按实际经过时间判断超时，失败不提交部分偏移并继续正常采集。
启动测量见startup-optimization.md；当前EEPROM流程和操作步骤见imu-eeprom.md。

| 栈总量 / 历史最小余量 | 当前 lvgl 4096B、sensor 2048B、touch 1024B、IDLE 512B；FreeRTOS 栈填充值扫描结果乘 sizeof(StackType_t)，转换为字节 |
| 栈占用峰值 | 总量减历史最小余量，是填充值法估计值，不是当前即时栈指针用量 |
| CPU 百分比 | 相邻诊断快照之间的 FreeRTOS 运行计数差 / 总计数差；调度归属时间包含 ISR，不是剥离所有中断后的纯任务执行时间 |
| 任务周期 | 连续两次业务循环开始的间隔，最近/历史最小/历史最大，单位 us；首拍尚无间隔。Idle 无固定业务周期，不伪造循环指标 |
| 处理耗时 | 循环开始到处理完成，排除末尾周期等待，包含被抢占、内部等待和诊断发送时间，最近/历史最大，单位 us |
| 超预算 | 单次处理耗时大于本轮target_ms预算；lvgl/sensor/touch按场景动态选周期，它不是全部调度截止时间违约的计数 |
| 传感器读成功 / 未就绪 / 错误 | 来自真实读取结果，分别统计；传感器未就绪不会计为通信失败 |
| 数据年龄 / 成功间隔 | 从最近成功读取起经过的 HAL 毫秒时间、两次成功读取的间隔；尚无成功读数显示 --。读取成功不保证器件内部完成了新一次转换 |
| 读取耗时 | 实际驱动读取前后计时，100us 分辨率；包括抢占。SPL006 包含既有压力补偿调用，ADC 包含启动、转换等待及停止 |
| RTOS / LVGL 内存 | FreeRTOS 堆当前/历史最小剩余；LVGL 池当前剩余/诊断快照观测到的最大占用，全部为字节。短于快照间隔的瞬时峰值可能遗漏 |
| 心率队列丢弃 | 32 帧队列满时丢最旧帧的累计次数；STOP、重新 START 或故障清队列属于原流程，不计入溢出 |
| 心率 UART 成功 / 失败样本 | 真实 C 发送函数的返回结果，按发送批次的样本数量统计；成功只证明字节交给模块，不证明手机收到 |
| 手机 CRC / 序号缺口 | 诊断帧 CRC/格式拒绝和已接收帧之间的序号缺口；缺口可能来自板端 UART 失败或后续链路，需对照板端计数 |

MPU6050、LSM303DLHC、EM7028、SPL006、AHT21 和电池 ADC 分开显示。EM7028 初始化字段在 START 时更新为最近启动配置结果。
返回码沿用各驱动枚举；SPL006 将压力返回码放低 8 位、温度返回码放次低 8 位，0x10000 表示压力补偿失败。
AHT21 触发命令成功不算读取成功，触发失败计入错误；忙轮询计入未就绪，最终超时计入错误。电池初始化 0 表示服务初始化完成，转换是否正常应看读取结果。

## 实测建议

先静置 30 秒，再持续滑动/切换页面 30 秒，然后开心率 60 秒并导出两种 CSV。
观察 sensor 周期是否明显超过 10ms、成功读取间隔是否拉长、读取/初始化错误是否增加、心率队列和 UART 失败是否增加。
气压器件 1Hz、1s 轮询，未就绪较多属于预期；AHT21 约 2 秒一轮，心率读取下限 30ms，不能统一按10ms判断所有器件。MPU仍为100Hz，DATA_RDY有效才计成功，每次服务最多发布一帧。成功计数表示实际取得的新帧，不代表器件生成的全部帧；普通寄存器被新样本覆盖不会产生I2C错误。

常规轮询观察MPU的`gap_max_ms`、`work_max_us`和sensor任务周期；读取间隔超过10ms提示可能跳过中间样本，但没有硬件帧号时不能精确统计漏采帧数。`errors`只表示驱动返回失败，`not_ready`表示本次未取得新帧，均不能替代完整采样率测量。
栈余量应在页面切换、校准、传感器失败等实际高负载路径后再观察。

诊断复用原 USART1 中断异步发送：每 100ms 最多一帧 30～78 字节，约 2.6～6.8ms 线速时间，超时预算仍为 10ms，在 LVGL 循环轮询时检查。
帧保存在固定静态缓冲中，UART完成后才累计成功；超时或断电累计失败，HAL_BUSY不推进本行和序号。关闭发送后仍收取在途帧结果。
调试版心率每次最多2帧，以静态缓冲异步发送；心率与诊断各自收取自己的完成结果，未收取结果前其他异步发送等待。AT/业务写入不会穿插到在途帧中，RX继续使用原接收中断和环形缓冲。
当前4个任务（含IDLE）+6个传感器+系统/启动/MPU EEPROM/MPU校准判定记录，一组约1.4秒、868字节；没有printf、动态分配或新增发送任务。
诊断不再在 LVGL 任务忙等 UART 线速时间，但打包、快照和发送中断仍占用 CPU。可关闭发送一段时间再开启，对照 CPU 窗口、最近周期和成功读取间隔；历史极值不会因开关而清零，干净的重复实验需重启。
CPU 计数器约 119 小时回绕，本内核在回绕处的运行统计不保证准确；长时间实验应在此前重启，不把该窗口作为精确 CPU 统计。

## 协议与导出

WDG1 二进制帧：4 字节 ASCII 标识、类型 uint8、对象 ID uint8、帧序号 uint16、板端快照时间 uint32、若干 uint32 字段、CRC16。
全部多字节字段小端。CRC 为 CRC-16/CCITT-FALSE（多项式 0x1021、初值 0xFFFF、无反射、无最终异或），覆盖帧头和数据。
类型 1 任务含 14 字段，类型 2 传感器含 10 字段，类型 3 系统含 16 字段，类型 4 启动含 16 字段，类型 5 MPU EEPROM含 4 字段，类型 6 MPU校准判定含 16 字段；确切顺序见 DiagnosticParser.FIELDS及imu-eeprom.md。
无有效采样时 sample_age_ms=0xFFFFFFFF。任务 ID：0 lvgl、1 sensor、2 IDLE；传感器 ID 依次为 MPU、MAG、HEART、BARO、AHT、ADC。
同一组记录使用同一个快照时间；各传感器在短临界区分别取一致快照，并不是所有器件同时转换。

手机在原 SPP/BLE 接收副本上解析诊断并将剩余字节交给原 JustFloat 波形解析器，不新增 socket 消费者。
支持任意拆包、粘包、CRC 拒绝及后续帧恢复。损坏诊断帧返回原字节流用于重新同步，可能使相邻一帧波形被旧 JustFloat 解析器拒绝；正常完整诊断帧不进入波形解析。
CSV 是长表：phone_elapsed_ms,device_ms,sequence,type,name,field,value。phone_elapsed_ms 为手机完整诊断帧到达时间，device_ms 为板端快照时间，字段名称包含单位；未知值原样保存 4294967295。
手机不保存无限时长记录，最近 1024 帧以外的历史会淘汰。关闭页面仍接收；重连清空旧诊断数据。

## 2026-10-21：触摸滑动时 MPU6050 链路中断（FIFO版本历史记录）

现象：触摸滑动时 MPU6050 数据消失，界面显示 `NO IMU DATA`、pitch/roll/yaw 变 `--`，松手后自行恢复；磁力计读数正常。

当时的FIFO版本定位到时间戳与新鲜度判定组合，以下机制和主机数值为历史记录；当前已关闭FIFO，不再执行这条积压路径：

1. `mpu6050.c` 从 FIFO 深度回推每帧时刻（`next_ms = counted_ms - (深度-1)×10ms`），一次服务最多取 8 帧，剩余留在器件里。
2. 任务被抢占造成的积压越大，这一批帧的估算时刻越旧。主机套件实测（磁刚读成功后压入不同帧数、跑一次服务）：

   | 压入帧数 | 服务后剩余 | imu_online | mag_online | 末帧时刻 |
   |---|---|---|---|---|
   | 12 | 4 | 1 | 1 | −40ms |
   | 14 | 6 | **0** | 1 | −60ms |
   | 20 | 12 | **0** | 1 | −120ms |

3. `app_imu.c` 用 `HAL_GetTick() - s_last_sample_ms < 50ms` 判在线，而 `s_last_sample_ms` 是上面的回推时刻，于是"帧一直有、却追不上窗口"被当成没有数据。阈值 14 帧约等于 140ms 的连续积压。

现场判据：`mpu_fifo.depth_max` 到 10～14、`overflows` 不增长、MPU 成功读取间隔同步拉长 → 只是积压，帧没丢；`overflows` 增长 → 积压超过 1024 字节（85 帧）真丢帧并进入重建。

后续先将sensor优先级从2提高到3，用户实板反馈数据恢复正常，但触摸流畅度下降；移除分块固定等待后，用户仍选择改用常规轮询。

当前状态：关闭FIFO和溢出中断，保留DATA_RDY；一次读取0x3A..0x48共15字节，成功且有新帧才更新输出。移除FIFO缓存、计数/回推时间戳与批量解算；短时dt按有效读帧间隔，达到50ms的断采不外推。校准、EEPROM、磁融合及逐拍恢复保留，UI滤波100ms/限速360°/s保持不变；调度恢复为LVGL优先级3、sensor优先级2，每个显示分块前阻塞一拍。新增主机用例覆盖一次事务、只读最新帧、无新帧/部分读失败不发布、实际dt、长断采及tick回绕；触摸流畅度及实板动态误差待重新烧录确认。
