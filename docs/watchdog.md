# 外部看门狗 TPS3823-33 + BL1551B

用户已确认：恢复历史 `-O3` 并修正 WDI 启动高阻后，实板循环复位问题解决。以下保留排查过程中的历史记录；旧版归档与错误说明见 [version-history.md](version-history.md)。组合修复未逐项回退隔离。

PB2/WDI 每次喂狗输出一个高脉冲并回到低电平，PB1/WDG_EN 低电平将 TPS3823 RESET# 接到 MCU NRST，高电平屏蔽其输出。芯片监测 3V3，欠压阈值典型 2.93V；看门狗超时典型 1.6s，手册范围 0.9～2.5s；复位延时 120～300ms。

按 Core 原理图，BL1551B 是复位选路模拟开关：ENB 高时 A1 接 B，将 NRST 接到经 R29 上拉的 3V3；ENB 低时 A2 接 B，接入 TPS3823 RESET#。3V3 电源变换器是 TPS63020，PA3/POWER_EN 经 R17、D5 保持其 TPS_EN。

## 驱动接口

`interface/tps3823.h` 提供 `tps3823_init`、`tps3823_enable`、`tps3823_disable` 和 `tps3823_feed`。先执行 CubeMX 的 `MX_GPIO_Init`，再初始化驱动；接口由同一任务串行调用，不在 ISR 中使用。

`MX_GPIO_Init` 从最初就把 PB2/WDI 配置为无上下拉输入，`.ioc` 也使用 `GPIO_Input`，不预先输出低电平。初始化/禁用先将 PB1 拉高，再确认 PB2 为无上下拉输入。WDI 高阻时芯片内部产生脉冲，禁用超时检测；仅拉高 PB1 只会屏蔽复位，内部计时仍继续。屏蔽复位也同时屏蔽该芯片的欠压复位输出。

启用时保持屏蔽及 WDI 高阻，等待至少 301ms 覆盖正常上电复位延时，然后恢复 PB2 推挽输出、产生一次喂狗脉冲，最后拉低 PB1 接通保护。非 A 版 TPS3823 在复位有效期间收到 WDI 跳变可能锁住复位；若已经锁存，延时和重新下载固件都不能保证解锁，必须使 TPS3823 断电重上电。调度器运行时通过 `vTaskDelay` 让出 CPU，调度器未运行时使用 `HAL_Delay`；已启用时重复调用不会等待或额外喂狗。

手册依据为第 15 页 7.3.4 和第 17 页 8.2.2；[TI 官方工程师说明](https://e2e.ti.com/support/power-management-group/power-management/f/power-management-forum/769155/tps3820-phenomenon-for-reset-pin)明确指出非 A 版在 RESET 低时收到 WDI 信号可能保持复位直到掉电重上电。旧 `MX_GPIO_Init` 曾在驱动初始化前短暂把 WDI 配成推挽低；后续再改高阻不能撤销这个风险。

`tps3823_feed` 每次拉高 WDI，经 16 个 `NOP` 后拉低，因此每次调用都有一次有效下降沿。100MHz 下仅 NOP 部分即至少约 160ns，超过手册 100ns 最小脉宽；没有增加任务或定时器。这样不会因单次翻转只有隔次才产生下降沿，将两个较慢分块的间隔合并成一次超时。

## 任务接入

`App_Task_Create` 在创建任务前初始化驱动，保持保护禁用。LVGL 任务完成 LCD/触摸硬件初始化和界面建树后，在 `lv_refr_now` 提交首帧之前启用保护；首帧刷新卡住时不再等待 sensor 首轮才能接通复位。硬件初始化和界面建树仍在保护启用之前。

首帧刷新最多宽限 5s：通过显示移植层的任务侧进度回调，在渲染完一个新分块、即将提交该分块时检查 100ms 喂狗间隔。等待同一笔 DMA 不会重复调用进度回调，ISR 不喂狗。正常首帧总耗时可以超过 900ms，但有效喂狗下降沿间隔仍须小于芯片最短超时并留出余量；整个首帧超过 5s 则停止喂狗。

`lv_refr_now` 返回后切换到运行期分块回调，再单独开始 sensor 首轮初始化的 5s 窗口，首帧渲染不占用这段预算。到期仍没有 sensor 首轮进度就停止喂狗；该窗口不会在循环中重置。sensor 首轮完成后立即转入双任务进度检查，计数回绕不会重新进入启动宽限。

运行期每完成一个渲染分块，先 `vTaskDelay(1U)` 阻塞一拍，让低优先级 sensor 获得运行机会，再按 100ms 间隔及 sensor 新循环进度决定是否喂狗。DMA 可能在 CPU 渲染时已经完成，此时 LVGL 不会进入 DMA 等待；不能仅靠 DMA 等待保证 sensor 获得调度。每轮 `App_Display_Service` 单独计算 5s 的分块喂狗预算，超时后即使还有分块也不再通过回调喂狗。主循环完成本轮服务时仍执行原有进度检查。

这检测的是显示分块/服务和 sensor 循环是否继续推进；单个外设报错后任务仍能完成循环时会继续喂狗。LVGL 卡在同一分块时无人喂狗；sensor 卡住时进度不再更新，LVGL 也不再喂狗；连续分块却始终不返回的显示服务在耗尽 5s 预算后停止回调喂狗。没有增加任务、定时器或中断喂狗，也未改变原有任务优先级、周期常量和栈大小；每块新增的一拍等待会增加刷新总耗时。运行中不再调用启用函数，防止停滞时反复重置超时。

2026-10-17 修复的可复现路径：旧代码仅在首帧保留分块回调，首帧后撤掉回调。若后续一轮刷新耗时 1.5s/3s，且 DMA 在 CPU 渲染期间已经结束，显示任务既不分块喂狗，也不主动阻塞让 sensor 运行，正常渲染即可跨过最短 900ms 看门狗超时。主机回归在修改前触发超时间隔断言，修改后通过；这证明软件路径修复，尚不证明实板重启原因已排除。

LCD DMA 发起后 100ms 仍未收到回调时，显示任务将其认领为失败，经原有 DMA 停止和 HAL 清理路径确认缓冲区不再被访问，再释放 LVGL 刷新状态并请求完整重绘；DMA 未停止时不提前释放。超时认领使用短关中断区，阻塞中止和 LVGL 完成通知都在恢复中断后执行。SPI1 错误中断与 DMA 完成中断均配置为优先级 12，SPI1 向量转交 `HAL_SPI_IRQHandler`。首帧期间连续故障导致任务无法及时返回时，已启用的外部看门狗负责复位。

## 验证

运行 `python tests/watchdog/run.py` 从真实 `Core/Src/gpio.c` 的 `MX_GPIO_Init` 开始执行，再接入真实看门狗驱动，核对启动期间不驱动 WDI、复位选路极性、每次喂狗产生下降沿、高脉冲和调度器等待路径；此前仅从 `tps3823_init` 开始的桩漏掉了早期 GPIO 配置。`python tests/startup/run.py` 验证首帧前启用、1.5s/3s 长首帧及每块 500ms 的任务侧喂狗、首帧及 sensor 独立的 5s 宽限、双任务进度、100ms 周期、停滞及 tick/进度计数回绕。新增运行期用例模拟首帧后 DMA 无需等待的 1.5s/3s 连续渲染，在喂狗前后检查有效下降沿间隔小于 900ms，并检查 sensor 停滞及单轮渲染超过 5s 后停止喂狗。`python tests/sensors/run.py` 验证 DMA 超时边界、安全释放和迟到回调；`python tests/ui/run.py` 联合真实 LCD 驱动及 LVGL，丢弃首笔 DMA 回调并模拟分块渲染耗时，验证长首帧、任务侧分块回调、回调可替换/解除和完整重绘。主机桩不模拟芯片真实时序。

### 2026-10-17 再次复核

上一次板上复测仍然重启，分块喂狗不是已确认的完整实板根因。本次发现目标优化为 `Optim=1`，读取原输出目录全部 252 个 C 对象的内嵌 ArmCC 命令，实际均为 `-O0`；历史 HEAD 使用 `Optim=4 / -O3`。已恢复历史 `-O3`，不改变位延时循环次数、任务优先级或采样参数。关闭优化会同时放慢 LVGL、HAL 和软件 I²C；主机模拟的分块耗时不能证明 O0 下实板满足 900ms。

独立目录全量编译后，252 个 C 对象均确认为实际 `-O3`，Code 从 257732 降为 200324 字节，RO=93076、RW=1264、ZI=96736，0 错误、31 条 LVGL 库警告。反汇编确认 `tps3823_feed` 仍保留两次 GPIO 电平写入和 16 次 NOP 循环，不依赖未优化代码的函数调用开销维持脉宽。watchdog 和 startup 主机回归通过；未烧录，未生成 HEX。

按所提供原理图，U9 的 ENB/PB1 没有外部上拉/下拉；R29=10k 上拉的是 A1，不是 ENB。BL1551 手册第 2 页注 3 要求 ENB 不得悬空，而 MCU 复位期间 PB1 会成为高阻。该电路应给 ENB 一个外部确定电平（若默认屏蔽看门狗，则上拉到 3V3）；运行时 PB1 仍由 MCU 正常驱动。此项无法用运行后的内部上下拉或延时覆盖整个复位窗口。另需检查复位时 PA3 释放是否使 TPS_EN/3V3 掉电。

本次烧录后先断开电池、USB 和可能反向供电的调试器，确认 3V3 断电，再重新上电，排除非 A 版旧锁存残留。若仍复位，应同时测 PB2/WDI、U8 RESET#、MCU NRST 和 3V3：首次接通 PB1 就复位、接通后至少 900ms 才复位、3V3 先低于欠压阈值是不同路径；不能都归因于喂狗周期。
